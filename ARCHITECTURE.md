# idea-factory — System Architecture

idea-factory is a meta-repository that converts a one-line business idea into a working MVP
by orchestrating a virtual startup team of AI agents. It does not generate code from scratch —
it scaffolds battle-tested templates into a new downstream project, then drives an autonomous
build loop (ralph) through three phases: Prototype, Harden, Ship.

---

## Three Layers

### Layer 1 — Skill (`/start-company` trigger)

The entry point is a single OMC skill invoked as `/start-company <idea>`.

```
skills/start-company/
├── SKILL.md          # Execution flow: ANALYZE → SCAFFOLD → KICKOFF → BUILD → VALIDATE → HARDEN → SHIP
└── HARNESS-GUIDE.md  # Design rationale with evidence for every architectural decision
```

The skill is stateless from the user's perspective: one command starts everything.
Internally it is a four-step sequence (Analyze → Scaffold → Kickoff → Autonomous Build)
with the ralph loop powering the build phase.

### Layer 2 — Templates (scaffold into downstream)

All files that end up in a downstream project originate here:

```
templates/
├── CLAUDE.md.tmpl          # Per-project constitution (80-line limit enforced)
├── settings.json           # permissions.deny floor + defaultMode: bypassPermissions
├── agents/                 # PM, Developer, Designer, code-reviewer (50+ lines each)
├── hooks/                  # PreToolUse audit log + PostToolUse quality/size checks
├── scripts/                # create-pr.sh, pre-deploy-consensus.sh, run-architect.sh, etc.
├── documents/              # PRD, essence, CONTRACT, handoff templates
├── .github/workflows/      # CI, label-pr, token-health
├── .githooks/              # pre-push stale-review warning
└── cron-bot/               # Additional templates for trading/cron project types
```

Template variables (`{{SERVICE_NAME}}`, `{{TECH_STACK}}`, `{{TEAM_TABLE}}`, etc.) are
substituted during SCAFFOLD. The CLAUDE.md 80-line limit is enforced by a PostToolUse hook
(`check-claudemd-size.sh`) after every write.

### Layer 3 — Downstream Sync (`sync-manifest.json` + `sync-downstream.sh`)

After initial scaffolding, templates evolve. The sync layer keeps 10 downstream repos
current without manual copying.

```
sync-manifest.json           # Three classifications:
  managed   → files synced 1:1 from templates/ (22 entries)
  computed  → files generated by a script (e.g., merged settings.json)
  customized → per-project files that must NOT be overwritten (CLAUDE.md, agents/*.md, etc.)

downstream-registry.json     # 10 tracked repos with type and scaffold date
sync-downstream.sh           # Propagates managed files; skips customized entries
```

Changing any `managed` file in `templates/` without updating `sync-manifest.json` will
cause drift between the meta-repo and downstream projects.

## Agent Roles

Each agent is defined in `templates/agents/` and vendored into downstream projects at scaffold time.

| Agent | Model | Responsibility |
|---|---|---|
| `analyst` | Opus | Business analysis: market fit, risks, target users, differentiation |
| `architect` | Opus | Technical architecture: stack selection, structure, protected-file review |
| `critic` | Opus | Essence adversarial review: finds product drift from the core "Why" |
| `code-reviewer` | Opus | Two-stage code review: spec compliance → code quality (CRITICAL/HIGH block gate) |
| `developer` | Sonnet | Feature implementation inside the ralph loop |
| `designer` | Sonnet | UI/UX decisions, component design, design-system consistency |
| `pm` | Sonnet | Story management, backlog prioritization, CEO communication translation |
| `qa-tester` | Sonnet + Playwright MCP | Functional testing via real browser interaction (not code-only review) |

All gate reviewers run with `isolation: "worktree"` — a fresh project copy with zero
knowledge of the builder's reasoning. This prevents Evaluator Leniency (self-praise bias).

## Hook Pipeline (`templates/hooks/`)

Hooks are categorized by type and wiring:

| Hook | Trigger | Category | Behavior |
|---|---|---|---|
| `check-audit.sh` | PreToolUse (Bash) | Governance | Exit-0 audit log — appends `{ts, session, tags, cmd}` to `.claude/audit/YYYY-MM-DD.jsonl`. Never blocks. |
| `check-claudemd-size.sh` | PostToolUse (Write) | Quality | Warns if CLAUDE.md exceeds 80 lines. Non-blocking. |
| `check-quality.sh` | PostToolUse | Quality | Checks for common quality signals after file writes. |
| `check-loop-breaker.sh` | PostToolUse | Safety | Detects repeated failures on the same story; escalates after 3 attempts. |
| `check-decay-counter.sh` | PostToolUse | Quality | Tracks quality metric decay across sessions. |
| `check-pending-prs.sh` | Session start | Governance | Reminds about open PRs before new work begins. |
| `session-start-restore.sh` | Session start | Governance | Loads checkpoint + essence + decisions to restore context. |
| `stop-cost-summary.sh` | PostToolUse (Stop) | Governance | Summarizes token cost at session end. |
| `stop-learning-capture.sh` | PostToolUse (Stop) | Quality | Captures learnings from the session for future reference. |
| `audit-review.sh` | Manual / PostToolUse | Governance | Reviews the audit log for suspicious command sequences. |

**Invariant**: No PreToolUse hook may exit non-zero. Blocking hooks are architecturally
incompatible with autonomous ralph/autopilot loops (see HARNESS-GUIDE.md — v7.1 regression).

## Data Flow

```
/start-company "your idea"
     │
     ├─ ANALYZE (parallel, opus)
     │   ├─ analyst:   business analysis → service name, type, risks
     │   └─ architect: tech stack, team composition, project structure
     │
     ├─ SCAFFOLD
     │   └─ Copy templates/ → ~/{project}/
     │       Variables substituted, git init, initial commit
     │
     ├─ KICKOFF
     │   └─ 3-5 plain-language A/B/C questions to CEO
     │       → fills essence.md, PRD.md, tech stack
     │
     └─ BUILD MVP (ralph loop)
         │
         ├─ Phase 1 — Prototype (mock data, no real APIs)
         │   ├─ MVP-001 → MVP-00N: core features with mock data
         │   ├─ VALIDATE-001: Gate — 4 reviewers in isolated worktrees
         │   │   ├─ architect  (opus, worktree): structural defects
         │   │   ├─ critic     (opus, worktree): essence drift
         │   │   ├─ code-reviewer (opus, worktree): spec + code quality
         │   │   └─ qa-tester  (sonnet + Playwright, worktree): functional defects
         │   └─ HANDOFF-MVP: structured phase transition document
         │
         ├─ Phase 2 — Harden (real APIs, tests, security)
         │   ├─ Reads handoff-mvp.md first (context reset strategy)
         │   ├─ HARDEN-001 → HARDEN-006
         │   │   (real data, error handling, tests, security audit,
         │   │    .protected-files generation, quality-baseline.md)
         │   ├─ VALIDATE-002: Gate — same 4 reviewers, new worktrees
         │   └─ HANDOFF-HARDEN: structured phase transition document
         │
         └─ Phase 3 — Ship
             ├─ Reads handoff-harden.md first
             ├─ SHIP-001: GitHub repo + branch protection
             ├─ SHIP-002: 5-stage PR pipeline (create-pr.sh)
             ├─ SHIP-003: Deploy with 6-gate consensus (pre-deploy-consensus.sh)
             ├─ SHIP-004: Git hooks setup
             └─ SHIP-005: Final doc sync
```

## Quality Gates

### Gate Reviews (VALIDATE stories)

Two-pass evaluation pattern — defects first, scores second:

- **Pass 1 — Defect Hunt** (mandatory): adversarial framing, no scores allowed
- **Pass 2 — Structured Score** (optional, fresh context): 4 axes, any < 6/10 = auto-fail
- Gate passes when: total critical defects = 0 across all four Pass 1 reviewers
- All outputs saved to `.project/gate-results/VALIDATE-{NNN}.md`

### 5-Stage PR Pipeline (`scripts/create-pr.sh`)

1. Build — `npm run build` must pass
2. Code-reviewer artifact — must exist with matching commit hash
3. Codex Gate — cross-model review if Codex CLI available
4. PR Creation — auto-links issues, blocks feat:/fix: without issue number
5. Bot Polling — waits for bot reviews (configurable timeout)

### 6-Gate Deploy Consensus (`scripts/pre-deploy-consensus.sh`)

1. Build passes
2. No P0/P1 open GitHub issues
3. PM review — implementation matches intent (nonce-based prompt injection prevention)
4. QA approval — quality-baseline.md current
5. Dev approval — protected files have architect review
6. Final sign-off

### Quality Ratchet

After Phase 2, `.project/quality-baseline.md` records concrete metrics (build errors,
test count, bundle size, API fallback depth). Every subsequent PR must not regress any
baseline metric. Proven across 13 phases in market-dashboard-v5.

## Claude Code 2026-Q1 Integrations

idea-factory tracks Claude Code's Q1 2026 primitives and adopts them as they stabilize.

### 1M Context as Standard (2026-03-13+)

- Opus 4.6 / 4.7 and Sonnet 4.6 treat 1M tokens as the default context window at standard pricing (the prior 2x multiplier was removed).
- Max / Team / Enterprise: on by default. Pro: opt-in via `/extra-usage`.
- **Implication**: SCAFFOLD + BUILD phases no longer need aggressive `/compact` calls until usage exceeds ~80%. The whole generated MVP typically fits in one context.

### /rewind Checkpoint

- `/rewind` (shortcut: `Esc Esc`) rolls back the agent's last set of file edits within the current session.
- Works alongside git: git provides committed history, `/rewind` provides in-session undo before commit.
- **Implication**: autonomous ralph loops can attempt risky changes with a zero-cost undo. Recovery is 2-tier: `/rewind` first, `git reset` as fallback.

### Opus 4.7 Tokenizer Inflation

- Opus 4.7 (released 2026-04-16) ships a new tokenizer. The same text counts up to +35% more tokens than Opus 4.6 at the same $5 / $25 list price.
- **Implication**: the Model Strategy (Sonnet default, Opus for architecture / RCA / deep analysis) tightens. Routine agents (`developer`, `pm`, `designer`, `qa-tester`) MUST stay on Sonnet 4.6. Gate reviewers (`architect`, `critic`, `code-reviewer`, `analyst`) run on Opus but only once per phase — not per story.

### SessionStart Hook + Larger Restore Payloads

- `templates/hooks/session-start-restore.sh` and `check-pending-prs.sh` fire on every new session.
- With 1M context, restore payloads can include handoff + essence + the last 10 decisions + the current story slate — no compaction pressure at session start.

### .claude/rules/ Pattern (Opt-in Rule Externalization)

- `templates/.claude/rules/{commit,security,code-style,ai-regression}.md` ship as starter rules that downstream projects can adopt as-is or adapt freely.
- Projects import rules via `@.claude/rules/*.md` references inside `CLAUDE.md` when the 80-line visible body would otherwise be exceeded.
- The four starters cover the highest-impact rule categories: commit discipline, secret hygiene, language-specific code style, and AI regression prevention.
- Classification: `customized` in `sync-manifest.json` — sync does not overwrite downstream edits, so teams can diverge without drift warnings.
- Why externalize instead of expanding `CLAUDE.md`: the 80-line limit is enforced by `check-claudemd-size.sh` and is a deliberate UX constraint (model-facing context budget). HTML comments in `CLAUDE.md.tmpl` are invisible to the model, so the import block costs zero tokens until uncommented.
- Activation path: uncomment the `@.claude/rules/*` lines in `CLAUDE.md` → Claude Code loads each file as an additional context source before the session begins.
- The scaffold flow (`install.sh`, `SKILL.md`, `phases.md`) is unchanged — rule externalization is opt-in, not default.

### Planned Adoptions (Week 3+ backlog)

- **Routines** (Anthropic, 2026-04-14): cloud-scheduled automation. One-line idea via GitHub webhook → full build without a local terminal.
- **Agent Teams + Worktree**: parallel workers across isolated worktrees, coordinated by a team-leader session. Requires `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`.
- **Plugin Marketplace**: package idea-factory as an official plugin (`anthropics/claude-plugins-official`) for one-command install.
